== THE DESIGN STATEMENTS, AS I UNDERSTAND THEM ==
(docs/design_statements.md is the user's; this is my reading of it,
which the user cannot do for me: "its not a checklist, i cant
interpret it for you". 2026-10-11. To be rewritten as I understand
more; the file itself is read again at the start of design work.)

What it is: a way of LOOKING, before and while deciding -- at the goal
as much as at the design. Not six checks to tick after the work: one
lens with six sides, turned on every part, and turned again on what
it shows (a statement can send me back to redefine the goal).

A system, in its words: things that do (processes), things done to
(processees), and the links between them.

- Epistemology. What I do not know and act on anyway becomes an
  assumption nobody said; then one nobody remembers; then a bug nobody
  can trace. The decay is the point: unknown -> implied -> forgotten
  -> harm. So an unknown is SAID, where it will be read, the moment it
  is met -- to the user, in AI.txt, in the commit. Guessing quietly
  and going on is the first step of the decay, however sensible the
  guess. (My "Decided on my own" list is this, late; earlier is better.)
- Change. Whatever moves makes unknowns: a format changed, and every
  reader of the old one is now wrong without knowing it; a thing made
  dynamic (attributes at run time, a registry at run time, mods) can
  no longer be known where the code is written. Each change: who still
  believes the old thing?
- Irreversibility. Nothing is done without losing something. A write
  loses what was there; a sum of an attribute loses which member
  changed; a queue loses who else wanted the cell; a summary of a
  session loses why. Ask what this action throws away and whether
  anyone needs it after.
- Tradeoffs. Speed, efficiency and correctness buy one another;
  nothing is free. If something looks free I have not found the price.
  Name which is being paid for which, then measure.
- Boundaries. The doer and the done-to are one thing cut in two, and
  WHERE it is cut is mine to choose: what the instruction knows and
  what the attribute's definer knows; what a rule does and what the
  simulation does; which superchunk owns what. A hard problem is often
  a cut in the wrong place (the pregnant sheep: an entity's act cut
  along a superchunk border).
- Links. With the cut made, the cost and the gain are in the join: the
  lookup from an instruction to the bytes it writes, the queue between
  superchunks, the walk to an attribute. Make the link cheap and both
  sides get faster.

HOW THEY GUIDE MY JUDGEMENT (the user: "the most important question
is: how can the statements guide my judgement?"). They do not decide
for me; they show what I am not looking at when I decide. I fail by
weighing too few things more than by weighing badly: left alone I
look at what I changed, what I made, what I gained, and the parts as
handed to me. Each statement points at the other side -- what I do
not know, who still believes what I changed, what I threw away, what
the gain cost, where else the cut could go, the join and not the
parts. So they come BEFORE the choice, to widen what is chosen
among, and again on the result; and on the goal before the design.
Example: for the pregnant sheep I proposed a general settle pass --
better inside the cut I was given (a queue a superchunk). The user
moved the cut (an entity's act is one stream wherever it lands).
Boundaries, asked first, would have put that on the table.

THE TYPE REGISTRY
- Dynamic, frozen per world before the server starts (REGISTRY FIRST:
  "the type registry is not initialized until a new world is created or
  an existing world selected for loading"); "registries are made new
  for each world opened and any old registries are completely
  dropped". IDs on demand for a new world, from types.csv for a saved
  one; "types.csv is the source of truth, for type registry loading"
  -- a saved name nothing registers fails. After freezing, lookups by
  ID; "the idea of the frozen registry is to downcast everything
  possible and remove all indirection".
- An ID is a kind byte and a 56-bit number, one number a type ("there
  is one type id for everything"); a plane's width and tile size are
  registration parameters, carried by its handle (LayerType { type_id,
  width_bits, tile_scale }).
- NAMES ARE FINAL (2026-10-24): "type id strings are final, that's why
  we have a file for them specifically"; "savefiles survive base game
  uodstes by the same mechanism"; "mods survive uodate thanks to
  types.csv". SHAPE IS NOT: "mods are expected to migrate their own data
  on world saves as needed. basegame will do the same as well".
- BUNDLES: every type in one; names namespaced by the registry
  (bundle::name; a bare name in a bundle is its own bundle's); nested
  bundles fine, "only the root level bundles need to be in the
  manifest"; "no 2 bundles can have the same name". A mod and a bundle
  are "logically the same thing". Sides: common ("server AND client",
  or shared libraries -- client calls live there), server, client;
  each bundle a single library ("1:1").
- REGISTRATION APART FROM CODE: "we really need to move types strings
  into the manifest, and just dont involve the libraries at all on type
  registration, just manifests" -- a library is opened only after the
  freeze, on its own side; "setup step (2) should not load any
  libraries". Hooks ("just another parameter on the registry types"):
  GeneratesTheWorld, RunsEveryTick, KeepsTheWorldHot, ShownByDefault.
- THE BUILDER (style guide, "not the final form"): builder::new()
  .new_bundle(..).add("grass", Grass).add(..).close_bundle() -- "a
  static string that csn ve written straight in the same function call";
  one function lists a mod's types and their code. Anything callable
  gets the side's handle at setup ("simulation handle, client handle, or
  both"), gathers what it needs and keeps it ("that downcasting example
  for rules is exactly the approach we need"). Reads are declared per
  rule at setup and fixed for now; a frame asks for the union of the
  active render rules' reads ("simple is better now").
- CLIENT CALLS: a ClientCall type a function, by ID, words in and out,
  between ticks, opt in ("basically a security feature"); callable in
  process too. A call gets its mod's config folder.

WORLDS
- THREE STEPS: create (the folder, superchunks/, mods/, mod_config/,
  world.csv with the seed -- "seed draw should.be happening on step 1"),
  set up (types.csv; mods into mods/ and basegame in or out, with
  runtime loading -- "never basegame" copied; leaving it out is "a
  separate flag"), run ("existing worlds just skip straight to run").
  Never run = no hot file. world.csv is format 7: format, seed, tick and
  the flag rows. "honestly, we csn slowly remove memory only worlds": no
  world without a folder.
- MOD CONFIG on disk alone, in <world>/mod_config/<mod>/, read by the mod,
  never the server; "if no config is provided worldgen can use a default
  config". A reset keeps the frozen registry: the world unrun and run
  again in its own folder.
- A server process runs one world; another world is another process. On
  client disconnect, everything is dropped and the client goes back to
  the main menu. Mods are folders, per world; "the files must be
  preinstalled on both client and servee beforehand"; a remote world's
  mods in client/worlds/<world>/.
- A world ID, the creation time and the name, in world.csv ("guaranteed
  to never conflict"): not written yet.

THE SIMULATION
- THE SIMULATION HANDLE owns a world's state and does everything to it:
  "server is a coordinator, not a doer"; "anythong in between ticks is
  internal simulation api". A rule gets a SimulationTickState (one
  superchunk's turn) and its RuleContext.
- SUPERCHUNKS ARE WHAT MATTER: 1024x1024 cells; a chunk (256x256) is
  "just a storage convenience to keep tessera happy". APIs by superchunk
  and CellIndex.
- WARMING, EXACTLY 256 TICKS: "superchunks must load in exatcly 256
  ticks after they start warming or the simulation stalls completely,
  never more, never less"; the server stalls at tick 255 for a job not
  done. Generating is warming ("instead of tsking the data from the save
  file we take it from the worldgen hook"): one warm job a superchunk,
  from the cooled arena, the store, or the worldgen hook, built off the
  tick into the arena's own Superchunk and the store's own
  SuperchunkEntities, adopted at the due tick. Never half generated.
  The worldgen writes through the server's own APIs ("thats what hooks
  are for"); writes outside its superchunk are not applied; entities
  through the store's builder, FirstWake making a wake before first hot
  impossible. Warming and cooling are the halos' job, forced hot and the
  camera too. A save and load as if nothing went cold ("thats exactly
  why we keep the list of hot chunks").
- ATOMIC COMPARE-AND-WRITES: every write under a compare, everywhere.
  SKIP TAGS (the user's design): SetSkipTag before a chain of compares;
  writes are methods of SkipTagSet only ("we can't have naked writes").

THE CLIENT
- Bevy is in the client's public API ("bevy is part of our public api
  wether we want it or not"); basegame's render rules and gui types are
  Bevy code ("bsse game can depend on bevy itself"; no shading language
  of ours). At the 0.7 freeze, Bevy pinned to its exact version.
- A render rule is code for one thing; the client loops ("we use the
  same approach server has"), at a detail level matched to the zoom; an
  image a superchunk a render layer, stacked by render layer number
  ("things that render should include a render layer number").
- THE INVARIANT: "the rendering main priority is not stalling the server
  at large zoom out levels, while keeping roughly the same fps, our fps
  target is 60"; "that's why today the server doesn't answer a whole
  frame at once at large zoomouts". Vsync on; "no graphic settings on
  the basegame".
- GUI: "a simple draggable windows with a grid inside", gui types
  nested by naming their parent, libraries for their dependants; the
  window system one, in the client.
- The window's test world: limitless, no sheep, the camera forcing
  superchunks hot.
- COMMS: TCP on loopback, port 11235 ("i like my fibonaccis"); one
  client for now, which alone may make, open, save, reset, pause; a
  client joining late gets the world's frozen types first;
  --close_if_no_clients (a 30 s wait) for a server a client started;
  a headless server given nothing prints its help.

MODS AND THE GAME FOLDER
- Two binaries: "the client always needs bevy, the server never needs
  ir"; "zero clients mods to load zero bevy code on server side". The
  game shipped as a folder: the binaries, the engine's libraries (each
  crate a Rust dylib, prefer-dynamic, $ORIGIN), libstd, basegame's
  library. "the game folder is static after compilation".
- THE MANIFEST: "in it we trust, if the libraries dont match the
  manifest we refuse to load / the manifest becomes the source of truth
  for the mod"; it names each bundle's entry, a struct implementing the
  bundle trait (Fabric's model: "the manifest file has a string that
  points to the entry point struct"). Load order by dependency, then
  name ("simple ordering by dependency and name is fine"); bundles list
  the bundles they depend on.
- BUILDING A MOD: against the game as compiled on the modder's machine
  ("we can expect modders to compile the game in their machines"),
  never its source; the engine's crates and the game's include fragment
  by plain relative paths ("cant we just work with paths", "Ideally we
  avoid any crstes.io interactions at all lol" / "and fail instead"); no
  Bevy in a mod's Cargo.toml (the kit route). "we want mod source code
  to be free of restraints"; the setup "simply specifying the root of
  civil egregore local repo". Mods never inside the game's repository.
- THE PACKAGERS: Rust binaries, std only, run by cargo aliases; "avoid
  using script files of any kind (cmd, shell, etc) and avoiding third
  party libraries". game_packager (`cargo package_game`) lays out
  target/civil_egregore/; mod_packager (to come) builds the game if need
  be, writes the manifest, lays out the mod in its own target/<mod>/.
  Release only for now. A mod template workspace in the tree, basegame
  "basically a copy of it".
- VERSIONS: now 0.6.5293 ("decided now. were on version 0.6.5293, why?
  idk", 2026-10-24): "we should have a single version on the root crate"
  -- the root Cargo.toml's alone; basegame "still follows the root
  version so it doesn't carry one of its own even if it acts as a
  separate workspace"; tessera its own (its own project). "freezing the public api will be our 0.7 moment" -- "the
  public api is stable for a given distributed version of the game,
  between versions it csn change, this is a game, not an operating
  system"; 0.7 the first version with mods, then content. Breaking
  changes "until 1.0 at least ... we probably going to get to 0.20
  before 1.0"; "why do we need versioning support and safeguards if we
  dont even have mods or saves to version?" World formats not
  stabilized: no backwards compatibility for saves yet.

- CDNF (the cdnf crate, 2026-10-25, its parser: "cdnf crate"): sections
  -- a colon at a line's start, as many closing, deeper by one colon,
  none skipped, a single colon not required and any number of them;
  elements -- text bodies (contiguous text, ended by a blank line, a
  dash, a section or a colon: "only double newline ia significant to end
  a text body, a single line is part of it"), lists (dashes at a line's
  start, blank lines between items allowed), pairs ("at the beggining of
  line is a section / at the middle or end of line is a pair with
  watever next element, there is no real distinction"; a b c is a (b c);
  blank lines before the next element allowed; "- a :" then "- b" is "a
  list inside a pair element inside a list"; "a triple newline terminates
  a list always, thats the only list special case" -- the innermost
  open, so a nested list ends and the one it is in goes on); quotes ("when a new
  element is expected, we can either parse a quoted text, or something
  else"), \" and \\ escaped; # comments; indentation means nothing; a
  comment-only line is no line at all. A tokenizer, then the parser
  ("i would make a tokenizer instead of going byte by byte"); one smoke
  test ("we dont need too much testing").
