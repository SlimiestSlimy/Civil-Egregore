== THE DESIGN STATEMENTS, AS I UNDERSTAND THEM ==
(my reading of docs/design_statements.md; "its not a checklist, i cant
interpret it for you". The file itself is read again at the start of
design work.)

What it is: a way of LOOKING, before and while deciding -- at the goal
as much as at the design. One lens with six sides, turned on every part,
and turned again on what it shows. A system: things that do, things done
to, and the links between them.

- Epistemology. An unknown I act on decays: implied, then forgotten,
  then a bug nobody can trace. So an unknown is SAID, where it will be
  read, the moment it is met: to the user, in AI.txt, in the commit.
- Change. Whatever moves makes unknowns: who still believes the old
  thing?
- Irreversibility. A write loses what was there, a summary loses why.
  Ask what an action throws away, and whether anyone needs it after.
- Tradeoffs. Speed, efficiency and correctness buy one another. If
  something looks free I have not found the price. Name it, then measure.
- Boundaries. Where the doer and the done-to are cut is mine to choose.
  A hard problem is often a cut in the wrong place (the pregnant sheep:
  an entity's act cut along a chunk border).
- Links. With the cut made, the cost and the gain are in the join. Make
  the link cheap and both sides get faster.

They do not decide for me; they show what I am not looking at. I fail
by weighing too few things more than by weighing badly. So they come
BEFORE a choice, to widen what is chosen among, then again on the
result, and on the goal before the design.

== SETTLED (in force) ==

THE TREE (2026-10-26)
- The root is a virtual workspace. Its members: utilities (archive,
  chance, coordinates, dynamic_library, rng, ...), protocol (kinds,
  manifest_format, manifests, packages, simulation_time, type_names,
  type_registry), server (step 3 below), game_packager,
  game_distribution, mod_packager, and AI_SCRATCHPAD (mine; nothing
  depends on it). Workspaces of their own: tessera, cdnf (its rules in
  cdnf/cdnf.cdnf), and basegame (a common container mod: basegame_common
  and basegame_server). meadow lives outside the tree at ../meadow, the
  off-site mod. reference/ holds the old code and is not built: hindsight.
- Aliases: `cargo package_game`, `cargo package_mod <folder>` (and
  `cargo package_mod new <folder> <side>`), `cargo distribute_game`.
- Version 0.7.5. 0.8 will be the server, 0.9 brings diagnostics back. "the
  public api is stable for a given distributed version of the game,
  between versions it csn change". World formats are not stabilized.
- Third-party crates: libloading and sha2, declared once at the root.

PRINCIPLES
- No game content outside basegame. Zero hacks in the server ("we want
  hacks in basegame, not on server"). Avoid sync primitives where a
  borrow or a move will do. "delete dead code, we want to go to the
  bones". "each thing we add to make things simpler or leave them equal
  at least, thats tye reason we're building the game from the tail".
- Procs see type IDs, never internal indices: "wat a proc sees and talks
  with its typeids. not internal array indices".
- No floats in what a world follows from (clippy.toml): whole numbers,
  utilities::chance.

MODS (how and why in memory: mods-why-one-crate,
mods-built-against-the-compiled-game)
- A mod is one crate and one library (or none, for a container), with
  one side (common, server, client). Qualified names are `mod>type`, made
  only of A-Z a-z 0-9 _. A mod depends on its own side or common; "a
  container mod simply specifies a side to constrain its carried
  dependencies", and a common container may carry anything.
- premanifest.cdnf (written by hand) goes through the mod packager and
  becomes manifest.cdnf (written by the CDNF writer, with SHA-256 hashes
  `0x...`), all inside a stored zip. Dependencies' zips go in the mod's
  dependencies/, with versions on both sides.
- THE CHAIN: CDNF, then protocol::manifest_format (the shared reader),
  then manifests (checks of one mod, then across mods), then the type
  registry (a flat list: IDs, qualified names, no checks). Then loading:
  libraries out of the zips, set up mod by mod, dependencies first. Each
  type's `set up` is #[unsafe(no_mangle)], named in the manifest.
- Kinds: common -- plane, attribute, client call; server -- entity,
  entity proc, sca proc, worldgen; client -- render proc, gui. An entity
  proc names its entity. A sca proc names its `planes` (one or more) and
  its `seconds per sample`. A plane says its `width` (1, 2, 4, 8, 16 or
  32 bits) and its `tile side` (1, 2, 4 and so on to 256 cells), held
  as the enums PlaneWidth and TileSide: no generics in the server ("we
  get type security benefits without flooding the server with
  generics"); the reader refuses any other number, `of_` panics.

THE SERVER (0.8; design in force)
- CHUNKS: a chunk is 1024x1024 cells (formerly the "superchunk"; "lets
  rename superchunks to chunks"). A CellIndex is the 44-bit chunk index,
  then the 20-bit place in its chunk, in Morton order. Threads work per
  chunk.
- HOT STORAGE: each chunk keeps only the planes that have a tile that is
  not 0, sorted by TypeId. Each plane is dense ("only sparse when we
  need it to be, ie later"), packed by width, in Morton order, with an
  exact count of tiles that are not 0 (sampling goes by it). A plane
  that empties is dropped at the tick's end. Tiles are aligned, with no
  shift.
- SAMPLING: "lets just use the count and loop over each value on a
  sampleable plane, completely wasteful, incredibly simple". The rate:
  "mean time per sample on simulation seconds per sampleable cell".
  Read as an exact decimal, no floats ("floating point numbers ... are
  not machine portable"), and rounded to a Chance per tick (out of 2^32;
  1 second at 256 ticks a second is 1/256). "the simulation second is
  chanhed in code to 128, and everything else simply derices from it" --
  protocol::simulation_time. Hits are Morton cell indices.
- THE INSTRUCTION: 32 bytes -- the opcode (u8) and the tile index (u32,
  its corner cell's Morton index in the chunk: "tile index (for morton
  index)"), the plane's type ID (u64), and the data ([u64; 2]). Public
  opcodes: compare (equality), write, skip tag. Internal ones, added at
  step 4 by a processing step at queue time: atomic and fence. "leta go
  with 32 bytes then"; measure it against split queues at 0.9.
- FLAT SKIP TAGS: a compare that fails skips past the next skip tag.
  Tags are unnumbered and never nest ("do we need to number skip tags at
  all? maybe not lol"); compares are duplicated where needed. "having
  many compares one after another all leading to the same skip tag is
  necessary to check larger pieces of data". HARD RULE: every write is
  under a compare, in every queue (memory: atomic-compare-and-writes).
- THE SCA PROC: `trait ScaProc: Any + Send + Sync { fn call(&self,
  server: &mut ServerHandle, sampled_plane_type_id: u64, tile_corner:
  CellIndex) }`. Its set up's TypeCode is a Box<dyn ScaProc>; mods reach their own type by
  upcasting to &dyn Any. "trait objects have to be, thats the crux of
  the server interface". Procs run by TypeId, each over its hits in
  Morton order.
- THE SERVER HANDLE: "basically a reference to all chunks (read only)
  plus the instructions queue references, 8 neighbor queues and the
  current chunk queue". Queuing is "just another type state construtor
  from the serverhandle". A bad instruction (not a plane, a value too
  wide) panics: "yeah panic that mf". READS: Result<u32, NotHot>. A plane
  the chunk doesn't keep reads Ok(0); a chunk that isn't hot, or one past
  the world's edge, is NotHot ("reada should fail on non hot chunks").
  Compares in a chunk that isn't hot fail.
- A CHUNK'S RANDOM STREAM: "a seeded random stream, which is where each
  chunk gets its random numbers from" -- RandomSource::for_stream(world
  seed, chunk index), taken for the tick and given back.
- ACROSS CHUNKS (step 4; the user's design, 2026-10-24/26): "we need
  compares on multiple queues to die together. thata were atomic compares
  come in". There are 9 queues, and each chunk applies only its own
  cells, in the one order. A set that spans chunks is gated by a counted
  atomic: "we need to count up to the amount of compares tied to the
  atomic, plus a bool that says if any failed so we abort inmediatly" /
  "at least 2 new types of compare, compare and update atomic and
  compare atomic (expected equals atmoc count, the last gate before
  writes are allowed to proceed)" / "an atomic is always tied to a skip
  tag". The lowering happens only where needed: "the public compare and
  write api is oblivious to superchunk boundaries". "yeah we have to wait
  on the atomic bruv"; a waiting chunk parks. "compares without writes
  are valid in this model". The tenth queue is gone. Entities across
  chunks: memory, entities-across-chunks-design.
