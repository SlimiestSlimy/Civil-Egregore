AI WORKSPACE -- this file is the AI's own: its notes, rules and open
threads for working on Civil Egregore, written for an AI first and a
person second. The AI keeps it current and may rewrite it whole; a
person reads it to see what the AI goes by. Plain text on purpose.

Docs that say the rest: docs/style_guide.md, docs/testing_protocol.md,
docs/glossary.md (one name per thing -- use its names, not the ones in
its "not" column), docs/design_statements.md.


== SESSIONS ==

LOCAL (the user's PC, has a screen)
  Bevy is built. The renderer is kept working, and running worlds are
  tested and measured in it: `cargo run --release`, a world made from
  the main menu. A run's census is server/transient_data/measurements/
  census.csv (ticks, the seconds they took, the pace, sheep, grass).

REMOTE (cloud, no screen)
  gui and renderer: only `cargo check --offline -p gui` / `-p renderer`
  (debug, no --release) is allowed. Never build, run, clippy or test
  them remotely; the renderer is run on the local machine.
  Never `--workspace` (it builds Bevy). Per crate:
    cargo test   --release --offline -p <crate>
    cargo clippy --release --offline -p <crate> --all-targets
  The root crate without Bevy, after checking
  `cargo tree -p Civil_Egregore --no-default-features --offline | grep -c bevy`
  prints 0:
    cargo clippy --release --offline -p Civil_Egregore --no-default-features --all-targets


== ALWAYS ==

- Never run `cargo fmt`; never `cargo clippy --fix` (both reformat).
- Testing, committing and pushing are separate commands: a test's
  output is read before the commit is made.
- Clippy warnings are cleaned before a commit.
- No test or tool has a seed written in it: all take the one in
  transient_data/seed.csv, rolled every 5 counted runs
  (utilities::seed; env `CIVIL_EGREGORE_SEED=<hex>` or `=fresh` for one
  run). A test holds on any seed; a changed test is checked on several
  fresh ones.
- Every command goes through the root program:
  `cargo run --release -- help` lists them.
- A doc gives a performance figure only where it explains an
  optimization, before and after.
- Renames: the language server where it is easier; folder names,
  package names and prose by hand.
- No file much past 300 lines: a longer one is split into child
  modules by concern, public paths unchanged (a test tier's topics
  into tests/<tier>/<topic>.rs, named by #[path]). After a split of
  hot code, count instructions before and after: a function moved to
  another module may stop being inlined (Window::around did).
- Names are long, human and descriptive, and the glossary's:
  context_odds, world_files, host_thread -- not odds, info, thread.
- The renderer never stalls on the simulation: it asks for frames and
  shows what comes, never waiting on the host, however far the
  simulation is behind the viewport.


== FILES ==

- Every text file kept is CSV (utilities::csv): a first row naming the
  columns; lines starting `#` are notes (a report's notes and `##`
  table titles, the census's seed), `---` a table divider. Seeds are
  written in hexadecimal (utilities::seed::hex). Settings and world
  files are read by name, in any order, missing rows filled by
  defaults.
- Binary is fine for world data. A saved world is a folder:
  world.csv (what it is), hot.csv (its hot, cooling and warming
  superchunks), and superchunks/ with two files a superchunk, named by
  its index in hex: <index>.image (its cells' layers, as the cold pool
  holds them) and <index>.state (its random numbers and its entities,
  attributes and all) -- terrain and entities kept apart.
- Not CSV and fine: tessera's saved worst bitmaps (.pbm, an image
  format), rendered .png, tool configs (.toml, .json).
- utilities/default_settings.csv and utilities/sliders.csv are written
  by hand; nothing generates them.


== WHERE THINGS GO ==

- A rule (entity_rules/, mc_rules/) reaches the simulation only
  through instructions/: what it lacks is added there.
- What is hot and for how long is the simulation's (simulation::halos);
  the server only defines it (server::hot_of -> simulation::Hot:
  About { entity, side, viewport } or Forced), hands over what
  generates a superchunk, and passes each frame's viewport to
  Halos::keep_viewport. With Hot::About.viewport (the world's camera
  loads superchunks) EVERY superchunk of the viewport is hot, unioned
  with the entity halos, independent of them -- no cap (the old 8x8
  CAMERA_SIDE was an unrequested invention, removed). Off: only the
  entities make superchunks hot.
- server owns a world's start (server::Start); the CLI and the gui
  both feed it.
- The renderer asks the host (server::host) for frames; the host never
  sends unasked. An ask is answered a few superchunks at a time between
  ticks (HostThread::answer_a_little, FRAMES_SHARE of a tick when there
  is no time to spare), each few a Frame, the last with more = false;
  the renderer shows every frame queued and asks again after the last.
  Nothing asked is dropped or capped to spare the ticks. Measured by
  `AI_SCRATCHPAD ticks_under_a_wide_viewport` (it waits for the world
  to settle first, or the baseline reads the world's making).


== WORDS (beyond the glossary) ==

- viewport: whatever the renderer should render, in superchunks; none
  in map mode. Everything else in the renderer uses Bevy's own terms.
  Our viewport is not Bevy's camera `Viewport`.
- map mode: toggled with M, at any zoom; no cells are asked for.


== FULL LOAD ==

The world is hot only about its hot entities. For a fixed load, make a
world with a side forced hot: in the renderer, the main menu's new
world, sliders' world group (side, forced hot, sheep a superchunk);
headless, `cargo run --release -- server new <folder> <seed> <sheep>
<side> 1`. Only a world with a side can be forced hot.


== SETTLED BY THE USER (2026-10-09) ==

- The tree rule is separate from worldgen: a generated cover drifting
  to the rule's own balance is the simulation, not a fault.
- No cap slider on the viewport's hot superchunks.
- Rules depend on `instructions` alone, and the instructions are the
  simulation's public API: they hand on no internals (no arena, no
  entities' store, no storage). The user rejected a module that
  re-exported those. Vocabulary types are at instructions' root.
- World formats are not stabilized: no backwards compatibility kept.
- A crate holds only what its name implies; mixing across crates is
  forbidden. Every world -- the program's, a test's, a tool's -- is
  made by server::start(Start { .. }), whatever it is to be: no mock
  world anywhere (one in `instructions` was rejected). A rule's tests
  and tools are therefore the server's (server/tests/fast/sheep.rs,
  grass.rs; server/src/diagnostics/), on worldgen's
  Generation::plain: flat, dry, no walls, no trees.
- The server is the starter and coordinator and generates nothing:
  worldgen says what is on each cell (generate_superchunk ->
  chunk_storage::SuperchunkCells), chunk_storage makes the image of
  them and keeps it cold, the server passes finished images and
  entity states between the managers and the disk. The renderer
  asks the server alone: server::host::frame for what is hot (its bit
  layout included), server::host::terrain_seen for the ground and the
  map where nothing is hot. It depends on server, gui, coordinates and
  utilities, and on nothing under the server.
- NOT KNOWING WHERE SOMETHING GOES: put it in `utilities` or in
  AI_SCRATCHPAD, TEMPORARILY (unless it really is a utility), and tell
  the user. What the program needs can only wait in `utilities`.
- AI.txt and the crate AI_SCRATCHPAD are the AI's to use freely.
  NOTHING MAY DEPEND ON AI_SCRATCHPAD. Probes go there as commands,
  not as temporary tests:
    cargo run --release -p AI_SCRATCHPAD -- <command>


== OPEN THREADS ==

- Worldgen is what a world's making and wandering cost: callgrind,
  2026-10-09, one thread (transient_data/measurements/
  profiles_2026-10-09/, with run.sh and every .out). Making a
  superchunk is 2.5 to 4 G instructions, some 60% of it
  worldgen::mesh::Mesh::blended and Mesh::locate's closure, then
  coordinates::cartesian_from_place and HeightMap::get. A world with
  no side run 3,000 ticks spent over 90% of its instructions
  generating the 12 superchunks its halos reached. Against that a
  tick of a 4-superchunk world with 8,000 sheep is ~0.33 M. The next
  optimization worth making is Mesh::blended.
- The tick reference (pasture 300 333 4000 4 1 less the 0-tick run)
  is 58.37 M instructions (8,680.05 M less 8,621.68 M) at 9303e37,
  the pasture a plain the server starts. It was 49.95 M on the mock
  pasture it replaced: another world, so the two do not compare.
- A world's stored image of a cooled superchunk is behind its cells
  until the writeback ring is flushed (World::write_back_and_flush_all,
  as a save does): compare images only after it. The complete tier's
  save/load test failed for that alone, since before 2026-10-09.
- A fresh flock loses ~2% at its first wake: old age is rolled for the
  whole sleep ahead (wake - now over LIFE_TICKS) and a fed sheep's
  first sleep is long. The rule as written; told to the user.
- Area allocator: 256 MiB blocks, 256-byte units, sorted interval list,
  owning handles (after the Tessera clean).
- Tessera deep clean: settle the code, move abstraction boundaries
  (the design statement on process and processee).
- Read every file: one name per thing, generalize repeats.
